## 반드시 지킬 것

- **읽기만 한다.** 파일을 고치거나 SQL 을 실행하지 않는다. 고칠 일은 보고만 한다.
- **건수만 세지 말고 id·이름을 하나하나 맞춘다.** 합계가 같아도 서로 다른 것이
  빠지고 들어와 상쇄될 수 있다.
- **직접 세어 확인한 것만 적는다.** "맞는 것 같다" 는 쓰지 않는다. 못 본 것은
  "확인 못 함" 이라고 적는다. 지어내면 사람이 다친다.
- 원본 xlsx 를 읽어야 하면 `python -I` 로 openpyxl 을 쓴다.
  Supabase 는 `redtag-01-schema.sql` 이 anon 에 SELECT 만 줬으므로 REST 로 읽는다.
  키는 `C:\Users\User\OneDrive\바탕 화면\GitHub\red-tag-manager\.env` 에 있다
  (읽어서 쓰되, 절대 보고서에 적지 않는다).
- PostgREST 는 한 번에 1,000행까지만 준다. 반드시 `Range` 헤더로 끝까지 나눠 받는다.
  이 함정 때문에 6.9kV 전체가 통째로 빠진 적이 있다.

## 무엇을 보는가

1. **누락** — 원본 배치가 넣겠다고 적은 id·행이 실물에 다 있는가.
   `equipment`, `switch_device`, `equipment_switch_map` 세 표 모두.
2. **초과** — 원본에 없는데 실물에 있는 것. 수기 추가분인지 찌꺼기인지 가린다.
3. **오기** — 이름·기기번호의 철자. 원본과 글자 단위로 다른 것.
   (전례: `HEAETER`→`HEATER`, `COUPLUNG`/`COUPLNG`)
4. **값이 바뀐 것** — 같은 id 인데 이름·위치·그룹·조작방향이 원본과 다른 것.
   사본의 09·10·11 같은 수정 파일이 의도적으로 바꾼 것은 수정으로, 설명 없이
   다른 것은 결함으로 가른다.
5. **수정분의 운명** — 사본에만 있고 원본에 없는 수정(09·10·11…)은 원본에서
   배치를 다시 만들면 덮인다. 그런 것이 몇 개이고 무엇인지 반드시 짚는다.
6. **연결 없는 것** — 점검대상이 안 붙은 조작대상, 조작대상이 안 붙은 점검대상.
   숫자와 함께, 그게 예비(SPARE)라서인지 자료가 덜 들어와서인지 가린다.
7. **빈 칸** — 위치·그룹이 비어 있는 것. 어느 배전반에 몰려 있는지.

## 보고 방식

한국어로, 표를 써서 짧게. 사용자는 전기 담당자이지 개발자가 아니다.

- **맨 위에 한 줄 판정**: 빠진 것 N건 / 어긋난 것 N건 — 또는 "빠짐 0, 어긋남 0".
- 그다음 표 하나로 표별 대조(선언 / 실물 / 빠짐 / 초과).
- 결함이 있으면 **무엇이 어떻게 다른지 구체적으로**. 기기명과 id 를 적는다.
  10건을 넘으면 처음 10건을 적고 전체 수를 밝힌다.
- 마지막에 **고칠 순서**를 중요한 것부터. 각 항목에 왜 그게 문제인지 한 줄.
- 결함이 없으면 길게 쓰지 않는다. 확인한 범위와 숫자만 적고 끝낸다.
- 추측과 확인을 섞지 않는다. 추측은 "확인 필요" 라고 따로 적는다.
